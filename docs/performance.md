# termit の応答速度を調べた記録

作成日：2026-09-09
対象：`ec5f0b8` 以降の実装、macOS（Apple Silicon）、release ビルド

## 1. 結論

「反応が遅い」という感触に対して工程ごとに測った結果、**端末自身の取り分は合計 1ms 前後**であり、
遅さの原因は描画でも VT 解釈でもなく、**描いたフレームが画面に出るまでの待ち**にあった。

| 工程 | 実測値 |
|---|---|
| 打鍵から画面内容が変わるまで（PTY の往復とグリッド反映） | 中央 **0.073ms** |
| 画面の更新を読み取ってから `present` を呼び終えるまで | 中央 **0.5〜1.3ms** |
| `present` から実際に表示されるまで | 直接は測れない。設定次第で **16〜50ms** |

最後の 1 行が支配的だった。
`desired_maximum_frame_latency` を 2 から 1 へ下げたのが、この記録で行った唯一の実質的な変更である。

## 2. 測り方

いずれも本体に組み込んであり、再現できる。

### 2.1 描画そのものの費用

```
termit --bench
```

ウィンドウを開かずに、実際の描画関数へ画面いっぱいの文字を流して測る。
毎フレーム内容を変えるので、字形の使い回しだけで速く見えることはない。

### 2.2 入力の往復

```
termit --latency-test
```

`/bin/cat` を PTY で起動し、1 文字書いてからそれがグリッドに現れるまでを測る。
経路は「書き込みスレッド → PTY → 行規律の echo → 読み取りスレッド → VT パーサ → グリッド」で、
利用者が打鍵してから文字が出るまでの、端末側の取り分にあたる。
キーボードを使わないので、画面操作の権限がない環境でも測れる。

### 2.3 実際の動作中の内訳

```
RUST_LOG=info TERMIT_FRAME_LOG=1 termit
```

1 秒ごとに次を出す。

- 読み取りスレッド：読んだ回数とバイト数、再描画の通知を送った回数と抑制した回数
- 主スレッド：通知の受信数、再描画要求数、実際に描いた数、読み取りから表示までの中央値と p90
- 描画：`prepare`、`acquire`、`encode`、`present` の内訳とセル数

## 3. 実測値

### 3.1 描画（`--bench`）

| 画面 | セル数 | prepare 中央 | submit 中央 | 合計 |
|---|---|---|---|---|
| 1280x800（163x47） | 7,661（全面） | 0.64ms | 0.46ms | 1.11ms |
| 1280x800 | 752（1 割） | 0.08ms | 0.31ms | 0.39ms |
| 1920x1200（245x70） | 17,150（全面） | 1.43ms | 0.93ms | 2.37ms |
| 1920x1200 | 1,680（1 割） | 0.17ms | 0.44ms | 0.61ms |

60fps の予算は 16.7ms である。
最も重い「1920x1200 の全面書き換え」でも 2.4ms で、予算の 15% しか使っていない。

**1 文字ごとに `TextArea` を積む方式は、遅さの原因ではなかった。**
実装前に疑っていたが、測ったところ費用は小さい。

### 3.2 入力の往復（`--latency-test`）

```
標本 60 件
中央 0.073ms  p90 0.112ms  p99 0.142ms  最大 0.177ms
```

### 3.3 動作中（1 行 65 バイトを 15ms 間隔で出す）

```
読み 42 回 2688 B, wakeup 送信 42, 抑制 0
wakeup=42 再描画要求=42 実描画=42 | 読み取り→表示 中央 0.8ms p90 1.1ms
prepare=0.45ms acquire=0.05ms encode=0.18ms present=0.02ms 合計=0.70ms
```

読み取り 42 回に対して描画 42 回。取りこぼしも溜め込みもない。

### 3.4 大量出力（15.6MB を `cat`）

```
読み取り 15,475 回 15,800,390 B（約 1 秒で消化）
wakeup=17 再描画要求=19 実描画=19 | 読み取り→表示 中央 16.2ms p90 16.7ms
prepare=0.82ms acquire=9.18ms encode=0.29ms present=0.04ms 合計=10.34ms
```

15.6MB を約 1 秒で消化し、そのあいだ 19 フレームを描いた。
1 回の読み取りごとに描くのではなく、描いていないあいだの更新はまとめている。
`acquire` が 9ms へ伸びるのは、走査の間隔を待っているためで、これは想定どおりである。

## 4. どこに時間が消えているか

打鍵から文字が見えるまでを分解すると次のようになる。

```
打鍵
 └ 端末がキーを PTY へ書く ─────────────┐
 └ シェルが echo して返す              │ 合計 0.073ms（実測）
 └ VT パーサがグリッドへ反映 ───────────┘
 └ 読み取りスレッドが再描画を通知 ───────┐
 └ 主スレッドが描いて present を呼ぶ    │ 合計 0.5〜1.3ms（実測）
 ───────────────────────────────────────┘
 └ present したフレームが表示される ──── 16〜50ms（設定次第、直接は測れない）
```

最後の段だけが二桁 ms である。
ここは端末の作りではなく、**表示装置と合成器の都合**で決まる。

Apple の開発者フォーラムによれば、`CAMetalLayer` の `maximumDrawableCount` が 3 のとき、
CPU から表示までの遅れは **50ms、30ms、16ms のあいだで揺れる**。
2 にすると、描き終えたフレームは次の走査で表示されることがほぼ保証される。

wgpu の `desired_maximum_frame_latency` はこの値に対応する。
termit は既定の 2 を使っていた。**1 へ下げた。**

## 5. 打った手

**`desired_maximum_frame_latency` を 2 から 1 にした。**
投入したフレームが次の走査で出るようになる。この記録で最も効く変更である。

**表示方式を環境に応じて選ぶようにした。**
Mailbox が使えれば選ぶ。ただし手元の Mac では `[Fifo, Immediate]` しか報告されず、Fifo のままだった。

**`window.vsync` を設定に足した。**
`false` にすると Immediate になり、走査を待たずに表示する。
待ちは消えるが、書き換えの途中が見えることがある。
Ghostty は macOS でも Linux でも既定で走査に合わせておらず、TUI では裂けが見えると明言している。
kitty も `sync_to_monitor no` を、遅延を詰めたい利用者向けの設定として挙げている。

**隠れているときに空回りする不具合を直した。**
ウィンドウが他の窓に隠れると `get_current_texture` が `Occluded` を返す。
これまではその場で再描画を要求し直しており、隠れているあいだ要求と失敗を際限なく繰り返していた。
次の出来事まで待つように変えた。

**設定と履歴の置き場所を直した。**
macOS の `dirs::config_dir()` は `~/.config` ではなく `~/Library/Application Support` を返す。
README には `~/.config/termit/config.toml` と書いてあり、実装とずれていた。
XDG の作法（`$XDG_CONFIG_HOME` または `~/.config`）に合わせた。
この記録の調査中は、設定が読まれないまま測っていて、原因を取り違えかけた。

## 6. 打てるが打っていない手

**損傷追跡（damage tracking）**
alacritty も foot も、変わった行だけを描き直す仕組みを持つ。
`alacritty_terminal` は `TermDamage` を提供しており、termit はこれを使っていない。
ただし 3.1 節のとおり全面書き換えでも 2.4ms なので、いま入れても体感は変わらない。
入れる価値が出るのは、4K や 6K で全面を毎フレーム描くようになったときである。

**行単位のまとめ描き**
alacritty は 1 回の描画命令で最大 65,536 個の字形を送る。
termit は 1 セルにつき 1 個の `TextArea` を積んでおり、命令の数では大きく劣る。
それでも 2.4ms で収まっているため、いま作り替える理由はない。

**`presentsWithTransaction`**
Apple のフォーラムでは、遅延を詰める設定として `maximumDrawableCount = 2` と併せて挙げられている。
wgpu からは触れない。触るには Metal の層を直接持つ必要があり、
「VT 解釈もウィンドウ管理も既存のものに委ねる」という方針から外れる。

**キー入力のたびに描いている点**
いま、キーを押すと echo が返る前に一度描いている。
内容は変わっていないので無駄である。ただし費用は 0.5ms 程度で、遅さの原因ではない。

## 7. この調査で分かった、測り方の落とし穴

**設定が読まれていないことに気付かず、3 回測り直した。**
出力を出すためにシェルを差し替える設定を `~/.config/termit/` へ置いたが、
実装は `~/Library/Application Support/tex/` を見ていた（当時の名前）。
その結果「11 秒で 1 フレームしか描かない」という数字が出て、深刻な不具合に見えた。
実際には、何も出力していないシェルを正しく待っていただけだった。

**画面キャプチャの権限がない環境では、GUI の状態を目で確かめられない。**
オフスクリーンに 1 フレーム描いて PNG に落とす `--probe` を先に用意してあったため、
描画そのものは確認できた。計測でも同じ方針が効いた。

## 7.5 セッションを増やしたときの重さ（2026-09-09 追記）

セッションを 23 本まで増やしたところで「とても重い、メモリリークではないか」という
報告があった。測った結果を残す。

### 漏れてはいない

40 万行を 1 本のセッションへ流し続け、2 秒ごとに RSS を見た。

```
開始 RSS = 11184 KB（上限 10000 行 x 40 桁 x 24 B = 9600 KB）
 2s: history=10000 行  RSS=21840 KB
10s: history=10000 行  RSS=21088 KB
20s: history=10000 行  RSS=20080 KB
```

スクロールバックが上限に達したところで頭打ちになり、その後は増えない。
**漏れはない。**

### 上限は本数に比例する

`alacritty_terminal` の `Cell` は 24 バイトで、行は内容によらず桁数ぶん確保される。
したがって 1 本あたりの上限は次のとおり。

```
スクロールバック行数 x 桁数 x 24 バイト
```

既定の 10000 行を 200 桁で使うと **1 本あたり 48MB**、23 本すべてが埋まれば **1.1GB** になる。
漏れではないが、本数を増やす前提の端末で 10000 行は大きい。
多く並べるなら `~/.config/termit/config.toml` の `scrollback` を下げるのが効く。

### 桁を変える費用も本数に比例する

左ペインの境目を掴んで動かすと、桁数が変わるたびに全セッションのグリッドを組み直す。
70 桁ぶんの行で埋めた状態で測った。

| 本数 | 履歴の合計 | 桁を 1 回変える費用 |
|---|---|---|
| 1 | 10000 行 | 1.9〜9.0ms |
| 4 | 40000 行 | 9.7〜16.5ms |
| 8 | 80000 行 | 30.6〜40.2ms |
| 16 | 160000 行 | 40.3〜53.7ms |

境目を掴んで引きずるあいだ、桁が変わるたびにこれがかかる。
16 本を超えると 60fps の予算（16.7ms）を大きく割る。

**（7.7 で直した。）**

## 7.7 引きずるあいだは、見えているものだけ組み直す（2026-09-09 追記）

7.5 で測った桁変えの費用は、引きずっている最中に全セッションぶん払っていた。
見えているのは 1 本だけなので、残りは手が止まってからでよい。

`Manager::resize_visible` が選んでいるセッションだけを合わせ、
待たせた大きさを覚えておく。手が 120ms 止まるか、境目を離した時点で
`Manager::settle` が残りを合わせる。待たせたセッションへ切り替えたときは、
描く前にそこで合わせる。

70 桁ぶんの行で埋めた状態で、同じ回で測り直した。

| 本数 | 履歴の合計 | まとめて（前） | 見えているものだけ（後） | 手が止まってから 1 回 |
|---|---|---|---|---|
| 1 | 10000 行 | 4.5ms | 4.6ms | 0ms |
| 4 | 40000 行 | 131.2ms | **3.1ms** | 10.7ms |
| 8 | 80000 行 | 131.6ms | **1.2ms** | 15.6ms |
| 16 | 160000 行 | 124.2ms | **1.3ms** | 31.1ms |

引きずっているあいだの 1 手が **124ms から 1.3ms** になった。

**（後日、これが原因の不具合を出した。7.10 を見よ。）**
本数に比例していたものが、比例しなくなっている。
組み直し自体が消えたわけではなく、手を離したあとの 1 回へ移しただけである。

### 見えていないものを描き直していた

見つかった本当の原因はこちらである。
`user_event` は、どの通知でも最後に `request_redraw()` を呼んでいた。
背景のセッションが字を出すたびに窓ぜんぶを塗り直していたことになる。
エージェントを何本も走らせるほど、見えていないもののための描画が増える。

窓に出ているのは、選んでいるセッションの画面と、左ペインの各行だけである。
`wants_redraw` で通知を選り分け、見えているものが変わるときだけ描き直すようにした。

| 通知 | 描き直す |
|---|---|
| `Wakeup`（画面の更新） | 選んでいるセッションのときだけ |
| `Title` / `ChildExit` | つねに（左ペインに出る） |
| `Osc(Cwd)` | つねに（1 段目のパスに出る） |
| その他の `Osc` | 選んでいるセッションのときだけ |
| `Command` | 選んでいるセッションのときだけ |
| クリップボード | 描き直さない |

## 7.6 CPU を実際に測った（2026-09-09 追記）

7.5 の変更で本当に減るのかを、窓を開けた状態で測った。

測り方は次のとおり。`XDG_CONFIG_HOME` と `XDG_DATA_HOME` を捨てて構わない場所へ向け、
覚える並びに 8 本ぶんの起動コマンドを書いておく。起動から 6 秒置いて落ち着かせ、
そこから 15 秒ぶんの CPU 時間を `ps -o time=` の差で見る。
「選り分ける前」は、`wants_redraw` を一時的に `true` を返すよう書き換えて測った。

| 状態 | 選り分ける前 | 選り分けた後 |
|---|---|---|
| 8 本とも何もしていない | — | **0.00s / 15s = 0%** |
| 静かな 1 本を見ながら、背景の 7 本が 10ms ごとに 1 行 | 0.89s = **5.9%** | 0.11s = **0.7%** |
| 8 本とも全速で出し続ける | 31.1s = **207%** | 34.1s = **227%** |

**背景だけが忙しいとき、8 分の 1 になる。** ここが直したかったところである。

**見ている 1 本も全速で出しているときは変わらない。** 当然で、
見えているセッションだけで描き直しの要求が絶え間なく立つため、
背景を止めても要求の数は減らない。差は測り誤差の範囲にある。

その 207〜227% は描画ではなく、飽和した PTY 8 本ぶんの VT 解釈である。
読み取りはセッションごとに別スレッドなので、核へ素直に散る。
実際の使い方でここまで出し続けるプログラムはまず無い。
参考までに、23 本を 2 時間開いていた実機のインスタンスは、
その間に使った CPU 時間の合計が **2.58 秒**だった。

何もしていないときに 0% で収まっているのは、
`ControlFlow::Wait` で寝ており、`Poll` で回していないためである。

## 7.7.5 何に時間を使っているかを見る（2026-09-09 追記）

推測をやめて、記号つきの実行ファイルを `sample` で覗いた。
`release` は `strip = true` なので、同じ最適化で記号だけ残す `profiling` を足してある。

```
cargo build --profile profiling
target/profiling/termit &          # 出力し続けるセッションを開いた状態で
sample <pid> 6 -file /tmp/sample.txt
```

出力し続けるセッションを 2 本開き、6 秒ぶんを取った。
本体の中に落ちた標本（合計およそ 470）の内訳は次のとおり。

| 場所 | 標本 | 割合 |
|---|---|---|
| `alacritty_terminal::Term::input`（文字をグリッドへ） | 181 | 38% |
| `Row::reset`（送りで行を消す） | 90 | 19% |
| glyphon の `glyphs_in_use` への挿入（1 字形につき毎フレーム 1 回） | 60 | 13% |
| 読み取りスレッド | 29 | 6% |
| `vte::Parser::advance_ground` | 19 | 4% |
| **既定の SipHash で `GlyphKey` を混ぜる** | **27** | **6%** |
| `Renderer::prepare_frame` | 17 | 4% |
| `draw_terminal` | 10 | 2% |

上の 2 つ（57%）は `alacritty_terminal` の中で、こちらから減らせない。
glyphon の 13% も、画面に出す字形の数に比例するもので、外からは動かせない。

**こちらの持ち物で減らせたのは、6% を占めていたハッシュだった。**

## 7.8 字形は添字で引く（2026-09-09 追記）

整形済みの字形は `HashMap<GlyphKey, Buffer>` に置いてあり、
1 コマにつき 2 回引いていた（用意するときと、置くとき）。
鍵は文字と太字と斜体の 3 つだけなのに、既定の SipHash で毎回混ぜていた。

`0x20..0x7f` の 4 体裁ぶんを配列に並べ、`(c - 0x20) * 4 + 太字 * 2 + 斜体` で直に引く。
そこから外れる文字（日本語や絵文字）だけを表に残し、その表も速いハッシュに替えた。
表のほうは 4096 を超えたら捨てる。大量に流したときの上限になる。

あわせて、画面のコマを一度 `Vec` に集めてから描いていたのをやめ、
読みながらそのまま描くようにした。1 フレームごとに
桁 x 行ぶん（1280x800 で約 300KB）の確保と解放が消える。
既定の地色のままの空白は、その場で飛ばす。

`termit --bench` を前後で 3 回ずつ交互に走らせた。
`submit` は GPU 待ちで散らばるので、CPU の取り分である `prepare` を見る。

| 埋まり具合 | 前（中央） | 後（中央） |
|---|---|---|
| 全面 7661 コマ | 0.67 / 0.65 / 0.65ms | **0.59 / 0.54 / 0.55ms** |
| 半分 3807 コマ | 0.34 / 0.33 / 0.33ms | **0.30 / 0.28 / 0.28ms** |
| 1 割 752 コマ | 0.08 / 0.08 / 0.08ms | **0.07 / 0.07 / 0.07ms** |

**描くための CPU が 15% 減った。**

出し続けるセッションを 2 本開いた状態の全体では、
15 秒あたりの CPU 時間は 12.3s から 12.3s で**変わらない**。
その場面では上の表のとおり VT 解釈が支配的で、描画の取り分が小さいためである。
効くのは、打鍵から表示までの間に挟まる描画の時間のほうである。

## 7.9 スクロールが途切れるという報告を測った（2026-09-09 追記）

「画面に文字が大量にあるときスクロールが途切れる」という報告に対し、
まず描画の速さを疑って測った。**速さの問題ではなかった。**
（本当の原因は行番号の取り違えだった。7.11 を見よ。
 測って絞り込めたのは「フレームは落ちていない」ところまでで、
 そこから先はスクリーンショットで分かった。）

出し続けるセッションを 1 本開き、`RUST_LOG=info TERMIT_FRAME_LOG=1` で 14 秒。

```
表示方式 Fifo（使えるもの: [Fifo, Immediate]）
描く面を取れなかった: 間に合わず=0 隠れて=1 作り直し=0
frames=60 平均 prepare=0.25ms acquire=16.27ms encode=0.09ms present=0.01ms 合計=16.61ms
1s: wakeup=60 redraw_req=60 drawn=60 | read→present p50 33.3ms p90 33.6ms max 33.9ms
```

- **描く面の取得に失敗した回数は 0。**フレームを落としてはいない。
- 60fps でぴったり出ている。ばらつきも無い（p50 と max の差が 0.6ms）。
- ただし 1 フレームのうち **16.27ms が `get_current_texture` の中**である。
  Fifo（垂直同期待ち）なので当然だが、そのあいだ催事の輪は止まっている。
  入力を捌ける隙間は 1 フレームあたり 0.3ms ほどしかない。
- 打鍵から表示までは 33.3ms、つまり 2 フレームぶん。
  `maximumDrawableCount = 2` である以上、1 フレームは避けられない。

失敗の回数を数える仕掛けを入れてある。`TERMIT_FRAME_LOG=1` を付けると、
取れなかった回を種類ごとに出す。次に起きたときはこれで切り分けられる。

### ついでに直した無駄

画面の中を探していないときでも、1 コマにつき 2 つの集合
（`find_cells` と `find_current`）を引いていた。
空でも鍵を混ぜる費用はかかるので、画面いっぱいで 1 フレームあたり
1.5 万回ぶん、まるごと無駄になっていた。探しているときだけ引く。

## 7.10 待たせた大きさが出てしまう不具合（2026-09-09 追記）

7.7 で「見えているものだけ先に合わせ、残りは後で」にしたところ、
**行数の足りない画面がそのまま出る**ことがあった。
画面の上のほうにだけ字が並び、下半分が地の色のまま残る。

穴は 2 つあった。

**待たせた分を合わせる合図が届いていなかった。**
`draw` の終わりで 120ms 後に起こしてもらうよう頼んでいたが、
起きたところで `new_events` は「描けずに待っていた」場合しか描き直しを求めない。
描かなければ `settle` は呼ばれないので、窓の大きさを変えたあとは
**選んでいないセッションが古い大きさのまま残り続けた**。
（同じ理由で、「動いている」印も消えないままだった。）
合わせ残しがあるとき、印が点いているときも描き直すようにした。

**選び方に素通りする道があった。**
`select` は出す前に大きさを合わせるが、`select_prev`（`⌘[`）だけが
`self.selected` を直に書いていた。古い大きさのセッションへ移ると、
そのまま描かれる。

**描く直前にも必ず合わせるようにした。** 選び方は何通りもあり、
どれか 1 つでも漏れれば同じ症状が出る。入口ではなく出口で担保する。

## 8. 参考にした資料

- [kitty performance](https://sw.kovidgoyal.net/kitty/performance/)：`repaint_delay`、`input_delay`、`sync_to_monitor` の意味と、遅延を詰める設定の組み合わせ
- [foot Performance](https://codeberg.org/dnkl/foot/wiki/Performance)：VT パーサの速さと、変わったセルだけを描く方針
- [Alacritty Rendering Pipeline](https://deepwiki.com/alacritty/alacritty/3.4-rendering-pipeline)：1 命令あたり 65,536 個のまとめ描き、1024x1024 の字形置き場、損傷追跡
- [Alacritty PR #5773](https://github.com/alacritty/alacritty/pull/5773)：損傷追跡の導入と、打鍵の遅延が目に見えて改善したという報告
- [wgpu SurfaceConfiguration](https://docs.rs/wgpu-types/latest/wgpu_types/struct.SurfaceConfiguration.html)：`desired_maximum_frame_latency` の意味と、1 にすると遅延が最小になること
- [wgpu PresentMode](https://docs.rs/wgpu/latest/wgpu/enum.PresentMode.html)：Fifo は約 3 フレームの待ち行列、Mailbox と Immediate は低遅延
- [Apple Developer Forums: How to schedule CAMetalLayer rendering for lowest CPU to Display latency?](https://developer.apple.com/forums/thread/711033)：`maximumDrawableCount` が 3 だと 50/30/16ms で揺れ、2 なら次の走査で出る
- [Ghostty: Let's talk about performance](https://github.com/ghostty-org/ghostty/discussions/4837)：既定で走査に合わせない方針
- [Ghostty Rendering System](https://deepwiki.com/ghostty-org/ghostty/5-rendering-system)：描画専用スレッド、6K でも 1ms 未満
- [glyphon](https://github.com/grovesNL/glyphon)：`prepare` で CPU 側の整形と字形の焼き付けを済ませ、`render` は描画命令だけを出す構造
- [Measuring terminal latency](https://www.lkhrs.com/blog/terminal-latency/)：Typometer による測り方と、macOS での各端末の比較
